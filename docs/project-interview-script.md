## 一、项目开篇介绍（⏱ 约 1.5 分钟）

面试官您好，我介绍一个我最近完整落地的一个项目：一个**基于大语言模型的电商智能客服系统**。

业务背景是这样的：电商场景下用户的咨询其实非常杂——有人要**查订单、查物流、申请退款**，这类是要按固定流程收信息、调接口办事的；有人问**商品和政策类问题**，这类靠检索知识来回答；还有人就是随便聊聊，甚至情绪上来了要骂两句；最后机器人搞不定的，还得能**平滑转人工**。所以它不是简单地套一个 ChatGPT 套壳，而是一个**多轨道的任务型对话系统**。

我在这个项目里主要负责三块：第一是**系统的整体架构设计**，用 LangGraph 搭了一套"路由—校验—执行"的对话引擎，业务流程全部用 YAML 配置化；第二是**全双工的接入层**，FastAPI 加 WebSocket，做了完整的转人工排队和坐席工作台；第三也是我觉得最有含金量的一块——我把系统里**调用频率最高的路由模型做了微调**，用 323 条自建数据把一个 Qwen3-1.7B 小模型练出来，接回系统后**格式合规从 94% 提到 100%，语义一致从 71% 提到 99%，双双反超了大模型基线**，路由延迟从秒级降到几十毫秒，而且随时可以一行配置回滚。

一句话概括这个项目：**它是一个"小模型管理解、大模型管表达"、流程可配置、状态可持久化、可转人工的生产级对话系统**。下面我展开讲架构。

## 二、系统整体架构（⏱ 约 2.5~3 分钟）

整个系统我分五层来讲。

**第一层是接入层。** FastAPI 提供服务，同时开了 HTTP 和 WebSocket 双通道。为什么要 WebSocket？因为客服场景有一个典型特点：**很多消息是服务端主动推的**——比如排队位置更新、坐席接入通知、坐席的回复，HTTP 的请求-响应模型做不了这件事。所以我设计了两个 WS 端点：`/ws/user` 给用户、`/ws/agent` 给坐席工作台，协议统一用带 type 字段的 JSON 消息，并带心跳保活。

**第二层是会话与转人工层。** 这层有两个组件：ConnectionManager 维护在线连接表，管"谁在线"；TransferManager 管转人工的完整状态机——每个用户会话有**机器、排队、人工三种模式**，申请转人工先进 FIFO 等待队列，坐席从工作台接入后绑定一对一关系。这里我特别处理了**可靠性**：用户断线时，排队中的自动出队、人工会话中的通知坐席回收；坐席断线时，他名下所有会话自动退回机器人模式，不能让用户对着一个已经不存在的坐席说话。

**第三层是对话引擎，也是整个系统的核心。** 我用的是 **LangGraph**，把一轮对话建模成一张图：主图上有 ingest、plan、validate、task、knowledge、chitchat、clarify 这些节点；而每一个业务流程——订单查询、物流查询、退款申请、商品推荐等等——是先在 YAML 里配置步骤和槽位，再由我写的 **FlowCompiler 编译成 LangGraph 子图**，像插件一样挂到主图上。这样做的好处是**加一个新业务流程不用改一行引擎代码**，写一份 YAML 就行。引擎里最关键的两个机制我后面讲流程时会展开：一个是 **interrupt 中断恢复**，用来做多轮收集槽位；一个是 **MySQL checkpointer**，以用户 ID 为 thread_id 把图的每一步状态持久化，服务重启、用户隔天回来，对话现场原样恢复。

**第四层是路由层，这里体现我的"分层模型策略"。** 每条文本消息进来，都要先过一个叫 **TurnPlanner** 的路由器，它输出一个固定 schema 的 TurnPlan JSON——判定这轮消息属于**任务、知识、闲聊**三条轨道中的哪一条，如果是任务轨道，还要给出 start、resume、cancel、set_slots 这四种命令和抽取出的槽位。这个路由器现在是**我微调过的 Qwen3-1.7B 小模型**，跑在自己部署的 vLLM 上，几十毫秒返回；而澄清话术润色、知识问答组织、闲聊这些**开放式生成**，继续走 qwen-plus 大模型。选这个分层策略的逻辑是：路由是**高频、结构化输出、有确定性兜底**的活，适合小模型；表达是低频、开放式的活，必须大模型——**各干各擅长的事，成本和体验同时最优**。

**最后一层是外部依赖。** 知识轨道通过一套 Provider 注册机制取数：订单、物流、商品这些**事实类数据走电商中台的 HTTP 接口**，FAQ 和 RAG 检索预留了标准接口随时可接。这样"知识"的口径永远来自业务库，而不是让大模型瞎编。

## 三、核心处理流程（⏱ 约 2.5 分钟）

我用一个具体例子把整条链路串起来，这样最清楚。

**第一轮，用户说"帮我查下订单"。** 消息经 WebSocket 进来，当前是机器模式，交给 DialogueApp——这是引擎对外的门面，负责一轮交互的完整生命周期。主图先走 ingest 节点把消息入栈，然后进 **plan 节点**：微调小模型判定这是任务轨道、命令是开启"订单状态查询"流程。接着进 **validate 节点**，这是我给系统上的确定性保险——校验器用纯规则检查：轨道是不是命中且只命中一条、命令类型是否合法、流程 ID 是否存在、需要卡片的意图有没有卡片。**LLM 负责理解，规则负责裁决**，模型再聪明也不允许它直接驱动业务。校验通过后进入流程子图，子图走到收集槽位的步骤，发现还缺订单号，就渲染提问话术然后 **interrupt 中断整图**——这是 LangGraph 的原生能力，中断点连同全部状态被 checkpointer 写进 MySQL，我把提问文案取出来推给用户。第一轮结束，图是"停"在数据库里的。

**第二轮，用户回"A123"。** DialogueApp 先查快照，发现图停在中断点，这条输入就**不再走路由**，直接包成 Command(resume) 去恢复那个 collect 节点——订单号这个槽位填上，子图继续走，调中台接口把订单查出来，以卡片消息返回。这里还有个体验细节：如果用户懒得打字、直接点了一张历史订单卡片，卡片上的订单号会**直接填进槽位，免掉一轮提问**。

**第三种情况，用户中途变卦，说"算了，先帮我退款"。** 路由识别出新的开启流程命令，task 节点会把**当前流程的槽位做快照压入暂停栈**，说一句"好的，先把订单查询放一放，我们处理退款"——之后用户说"继续刚才那个"，resume 命令能把快照弹出来接着办。还有一类很常见：**用户一句话问两件事**，比如"查下物流，顺便问下退货政策"。校验器会拒绝这种多意图，但我不直接丢弃——把第二个意图压进**挂起意图队列**，等当前流程走完，引擎主动追问一句"对了，你刚才还提到退货政策，需要现在处理吗？"这个细节对真实感提升非常大。

**最后是转人工。** 用户说"转人工"或者流程卡住，前端走 WS 发起申请，TransferManager 入队、推排队位置、坐席接入后切到人工模式——**之后这个用户的消息直接转发给坐席，不再进对话引擎**；会话结束双方各自退回机器模式。整个过程中引擎侧的对话状态一直由 checkpointer 维护着，转完人工回来接着聊，上下文一点不丢。

## 四、项目整体总结（⏱ 约 1.5 分钟）

最后总结一下这个项目的价值和我的收获。

**架构上**，这个系统经历了进化：早期我用自研的解释执行引擎跑流程、把对话状态整体序列化成 JSON 落库，能跑，但流程逻辑、中断恢复、持久化全要自己造轮子。重构到 LangGraph 之后，YAML 流程**编译期**就变成子图、槽位收集用原生 interrupt、状态持久化交给 MySQL checkpointer，我自己的代码只保留业务语义——**把不确定的工程问题交给成熟框架，把确定性留给自己的业务层**，这次重构让我对"什么时候该自研、什么时候该上框架"有了很实的判断。

**模型策略上**，"小模型管理解、大模型管表达"的分层被结果验证了：路由层微调小模型 100% 格式合规、99% 语义一致，反超大模型老师，延迟秒级降到几十毫秒，边际成本归零，且回滚只需改三行环境变量配置。中间那次 **bf16 合并事故**——合并后评测从 94%/71% 暴跌到 40%/0%，而所有静态检查全绿——我用排除法加教师强制 NLL 的行为实验定位到根因是合并精度抹掉了 52.8% 的 LoRA 增量，这段排查让我真正理解了"**所有静态检查都通过，只有行为测试说真话**"。

**工程习惯上**这个项目给我最大的沉淀是**评估基建先行**：动手微调前先建了 100 条人工核对的评测集、先跑出基线，正是因为有这个基线，事故才能在第一时间被发现、修复效果才能被客观证明。

这个项目从架构设计、前后端协议、对话引擎到模型微调和部署，是我一个人完整闭环的，我很乐意针对任何一层往深了聊。以上就是我的介绍，谢谢。
