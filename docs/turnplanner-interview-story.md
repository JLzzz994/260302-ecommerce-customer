# TurnPlanner 微调面试叙事手册

> 配套阅读：`turnplanner-finetune.md`（技术方案与阶段规划）、`turnplanner-bf16-merge-pitfall.md`（bf16 事故技术细节）。
> 本文档是"怎么讲"：三层结构——电梯版背诵用，完整叙事照着说，追问弹药防深挖。

## 一、电梯版（30 秒，必背）

> 我们的电商客服系统里有个每条消息必经的 LLM 路由器（TurnPlanner），原来调大模型 API，又贵又慢还有外部依赖。我把它换成微调的 Qwen3-1.7B：自建 323 条数据、LoRA 训练。中间踩了个很深的坑——**合并后的模型评测从基线 94%/71% 暴跌到 40%/0%，而所有静态检查全部通过**，最后用教师强制 NLL 三方对比定位到根因：**bf16 合并把小量级的 LoRA 增量量化抹掉了 52.8%**。改用 vLLM 运行时挂载 adapter 后，最终 100% 格式合规、99% 语义一致，**反超大模型老师**。

## 二、完整叙事（3~5 分钟，四幕结构）

### 第一幕：选点（为什么微调、为什么是它）

系统里有 5 个 LLM 调用点，我逐个评估了微调适配度，只挑了 TurnPlanner。理由三条：

1. **最高频**——每条消息必走，输入两三千 token、输出只有几十 token，延迟大头全耗在大模型 API 的 prefill 上；
2. **结构化输出**——固定 schema 的 TurnPlan JSON，监督信号天然可得；
3. **有确定性兜底**——自研 Validator 可当蒸馏数据的质检闸门。

其余四个点是开放式生成，微调性价比低。这就是**分层模型策略**：路由层用微调小模型，求确定、快、便宜；表达层（澄清润色/知识问答/闲聊）继续用大模型。

### 第二幕：数据与基线（先量化再动手）

80% 工作量在数据。写了"一鱼三吃"的脚本：场景工厂手工构造 22 个基础场景（三轨道 × 四种命令 × 卡片/长历史等覆盖矩阵），复用项目真实代码渲染提示词保证训练/推理分布一致，同义改写扩量到 323 条训练 + 100 条评测。**动手前先跑 teacher 基线：格式合规 94%、语义一致 71%**——没有基线的微调证明不了任何事。

### 第三幕：训练与事故

AutoDL 租 4090，ms-swift LoRA r=16/alpha=32，3 epoch 四分钟，loss 1.48 → 0.0006，token_acc 1.0——**训练侧一切完美**。合并、部署 vLLM、跑评测：**40% / 0%**。格式崩、语义全错、有的输出多一个 `}`。

### 第四幕：排查与翻案（高光，讲慢）

所有静态检查都是绿的，只能做排除法，每步有实验支撑：

- **环境？** 换本地 CPU + transformers 前向，错误一模一样 → 排除；
- **训练没收敛？** 日志完美收敛 → 排除；
- **数据坏/传输断损？** 双端 sha256 逐字节一致 → 排除；
- **chat template 错位？** 读 ms-swift 源码，训练渲染与部署模板逐字对齐 → 排除；
- **合并数学？** 张量级重建对比，196 个 LoRA 层误差只有 0.0011，当时判断为 bf16 舍入噪声放行——**这是我排查走的弯路，也正是真相藏身处**。

转折点是行为实验：用 swift 真实编码构造训练 token 序列，做**三方教师强制 NLL 对比**——

| 模型 | NLL |
|---|---|
| 裸基座 | 1.55 |
| **base + adapter 动态挂载** | **0.0004**（与训练日志 0.0006 精确吻合） |
| merged（bf16 合并） | 0.176 |

同一权重内容，两条路径差两个数量级，唯一变量是**存储精度**。再用 adapter 贪心解码，训练样本逐字复现——训练是好的、合并是坏的，铁证。

根因：LoRA delta 量级只有权重的 **0.21%**，bf16 尾数 7 位、相对量化步长 **0.4%**——`W + delta` 回存 bf16 时 **52.8% 的元素被舍回基座原值**。这解释了所有诡异现象：模型还记得紧凑 JSON 格式（delta 里最强的方向，幸存），语义分支点全被抹掉；训练时没事是因为 LoRA A/B 矩阵全程 fp32 存储，**坏只坏在 export 回存那一步**。

反直觉推论（金句）：**训得越好、delta 越小，合并越危险**——loss 压到 0.0006，恰恰把自己推进了 bf16 的量化盲区。

### 收尾：修复与流程沉淀

没重训——adapter 本身是好的。改用 vLLM `--enable-lora` 运行时浮点挂载，数学上与训练精确一致。最终：**100% 格式、99% 语义一致，双双超过大模型基线**，路由延迟秒级 → 几十毫秒，边际成本归零。

流程沉淀两条：合并产物上线前必做**训练样本贪心回放验收**（30 秒测试，本可第一天抓住问题）；精度敏感的合并存 **fp16** 不存 bf16。

## 三、追问弹药

### 数字速记表

| 数字 | 含义 |
|---|---|
| 323 / 100 | 训练 / 评测样本 |
| 94% / 71% | teacher 基线（格式/语义） |
| 40% / 0% | 坏 merged 成绩 |
| 0.0004 vs 0.176 | adapter vs merged 的 NLL（训练日志 0.0006） |
| 0.21% vs 0.4% | delta 量级 vs bf16 相对步长 |
| 52.8% / 9.8% | bf16 / fp16 的 delta 抹除率 |
| 100% / 99% | 最终成绩 |

### 高频追问

**Q：为什么不重训？**
坏的是合并精度不是训练产物，重训不解决精度问题；挂载路径与训练逐位等价，且 LoRA serving 保留了"一个基座挂多组实验 adapter"的迭代能力。

**Q：以后必须合并分发怎么办？**
三条正路：存 fp16（尾数 10 位、步长 0.05%，delta 是它 4 倍，抹除率降到 9.8%）；训练时 `lora_alpha` 提到 64 让 delta 越过 bf16 步长（治本、零成本）；无论如何合并后先跑回放验收再放行。

**Q：怎么想到是精度的？**（最见功力）
静态误差 0.0011 是噪声还是损伤，需要 ground truth 参照——训练日志的 loss 就是现成的。adapter 路径复现 0.0006 而 merged 只到 0.176，说明内容没变、行为变了，唯一变量是存储精度。**本质是把"合并正确性"从数学对比升级成行为对比。**

**Q：三层防御的 Validator 怎么没拦住？**
恰恰是这个 case 的教训：输出仍是合法 JSON、命令合法，schema 全过——典型 **valid-but-wrong**。三层防御挡结构错误，挡不住语义错误，人工标注的 eval 集才是最后真话。

**Q：323 条就够？**
结构化映射任务不是知识注入，22 格覆盖矩阵 × 变体扩量，eval 99% 说明该域内饱和；泛化边界清楚——加新流程就得补数据出 v2，或一行配置回滚大模型。

**Q：1.7B 会不会太弱？**
意图分类+槽位抽取是 NLU 任务，1B~3B 甜点区；同一 eval 集 99% vs 71% 反超大模型，选型是数据支持的。
